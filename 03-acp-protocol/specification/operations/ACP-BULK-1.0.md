# ACP-BULK-1.0 — Bulk Operations

| Field | Value |
|---|---|
| **Status** | Draft |
| **Version** | 1.0 |
| **Type** | Protocol Extension |
| **Depends-on** | ACP-CT-1.0, ACP-EXEC-1.0, ACP-LIA-1.0, ACP-LEDGER-1.2 |
| **Date** | 2026-03-10 |

---

## 1. Purpose

This document specifies batch authorization and bulk liability query operations for high-throughput ACP deployments.

In environments with large transaction volumes (payment platforms, trading systems, multi-tenant agent orchestrators), the unit authorization model of ACP-CT-1.0 can result in significant accumulated latency if each authorization requires an independent HTTP call. ACP-BULK-1.0 addresses this by enabling:

- **Batch authorization**: up to 100 authorization requests in a single HTTP call.
- **Bulk liability query**: retrieve liability records for multiple agents or time ranges in a single paginated operation.

Bulk operations do not modify the semantics of individual decisions. Each request within a batch is evaluated independently using the same rules of ACP-CT-1.0 and ACP-EXEC-1.0.

## 2. Batch Authorization API

### 2.1 Endpoint

```
POST /acp/v1/bulk/authorize
```

### 2.2 Request

```json
{
  "batch_id": "bat-uuid-7f3a1b",
  "requests": [
    {
      "request_id": "req-001",
      "agent_id": "agt-uuid-aaa",
      "action_type": "acp:action:financial.payment",
      "resource": "acp:res:account:12345",
      "context": {
        "amount": 500.00,
        "currency": "USD",
        "timestamp": "2026-03-10T14:00:00Z"
      }
    },
    {
      "request_id": "req-002",
      "agent_id": "agt-uuid-bbb",
      "action_type": "acp:action:data.read",
      "resource": "acp:res:dataset:analytics",
      "context": {
        "purpose": "reporting"
      }
    }
  ],
  "options": {
    "fail_fast": false,
    "partial_results": true
  }
}
```

#### Request fields

| Field | Type | Required | Description |
|---|---|---|---|
| `batch_id` | UUID | Yes | Unique batch identifier. Generated by the client. Used for idempotency. |
| `requests` | Array | Yes | List of individual authorization requests. Maximum 100. |
| `requests[].request_id` | String | Yes | Identifier for the request within the batch. Unique within the batch, not globally. |
| `requests[].agent_id` | UUID | Yes | Agent requesting authorization. |
| `requests[].action_type` | String | Yes | ACP action type to authorize. |
| `requests[].resource` | String | Yes | Resource against which the action is requested. |
| `requests[].context` | Object | No | Additional context for evaluation (amount, purpose, etc.). |
| `options.fail_fast` | Boolean | No | If `true`, stop at first DENIED or ESCALATED result. Default: `false`. |
| `options.partial_results` | Boolean | No | If `true`, return partial results when `fail_fast` triggers. Default: `true`. |

### 2.3 Response

```json
{
  "batch_id": "bat-uuid-7f3a1b",
  "processed": 2,
  "results": [
    {
      "request_id": "req-001",
      "decision": "APPROVED",
      "risk_score": 12,
      "reason_code": "CAPABILITY_MATCH"
    },
    {
      "request_id": "req-002",
      "decision": "DENIED",
      "risk_score": 87,
      "reason_code": "CAPABILITY_NOT_GRANTED"
    }
  ]
}
```

#### Response fields

| Field | Type | Description |
|---|---|---|
| `batch_id` | UUID | Same value as in the request. |
| `processed` | Integer | Number of requests processed (may be less than `requests.length` when `fail_fast: true`). |
| `results` | Array | List of individual results. |
| `results[].request_id` | String | ID of the corresponding request. |
| `results[].decision` | Enum | `APPROVED`, `DENIED`, or `ESCALATED`. |
| `results[].risk_score` | Integer | Risk score 0-100 computed by ACP-EXEC-1.0. |
| `results[].reason_code` | String | Decision reason code. |

### 2.4 Behavior with `fail_fast: true`

When `fail_fast: true`, the server stops processing upon encountering the first `DENIED` or `ESCALATED` result. Unprocessed requests do not appear in `results`. The `processed` field reflects how many were evaluated before stopping.

## 3. Bulk Liability Query API

### 3.1 Endpoint

```
POST /acp/v1/bulk/liability-query
```

### 3.2 Request

```json
{
  "query_id": "qry-uuid-...",
  "agent_ids": [
    "agt-uuid-aaa",
    "agt-uuid-bbb",
    "agt-uuid-ccc"
  ],
  "time_range": {
    "from": "2026-01-01T00:00:00Z",
    "to": "2026-03-10T23:59:59Z"
  },
  "limit": 1000,
  "cursor": null
}
```

| Field | Type | Required | Description |
|---|---|---|---|
| `query_id` | UUID | Yes | Query identifier. Used to retrieve additional pages. |
| `agent_ids` | Array[UUID] | Yes | Agent IDs to query. Minimum 1. |
| `time_range.from` | ISO 8601 | Yes | Start of the time range. |
| `time_range.to` | ISO 8601 | Yes | End of the time range. |
| `limit` | Integer | No | Maximum records per page. Default and maximum: 1000. |
| `cursor` | String | No | Opaque cursor from previous response to retrieve the next page. |

### 3.3 Response

```json
{
  "query_id": "qry-uuid-...",
  "total": 3450,
  "cursor": "eyJwYWdlIjoyLCJvZmZzZXQiOjEwMDB9",
  "records": [
    {
      "event_id": "evt-uuid-...",
      "agent_id": "agt-uuid-aaa",
      "event_type": "LIABILITY_INCURRED",
      "amount": 500.00,
      "currency": "USD",
      "timestamp": "2026-02-15T10:30:00Z",
      "institution_id": "inst-uuid-acme",
      "status": "SETTLED"
    }
  ]
}
```

| Field | Type | Description |
|---|---|---|
| `query_id` | UUID | Query ID. |
| `total` | Integer | Total records matching the query (across all pages). |
| `cursor` | String | Cursor for the next page. `null` if this is the last page. |
| `records` | Array | ACP-LIA-1.0 liability records for this page. |

---

## 4. Limits

| Limit | Value |
|---|---|
| Maximum items per batch authorization request | 100 |
| Maximum items per liability query page | 1000 |
| Bulk request rate limit per institution | 10 bulk requests/second |
| Maximum request body size | 1 MB |

Exceeding the 100-item limit in a batch authorization results in HTTP 400 with error code `BULK-001`.

---

## 5. Atomicity

### 5.1 Partial atomicity

Batch authorization operations use **partial atomicity**: each request within a batch is evaluated independently.

The batch is **NOT** atomic in the all-or-nothing sense. If 50 of 100 requests are approved and the other 50 are denied, the 50 approved ones are valid and the 50 denied ones are invalid. There is no rollback of approved requests due to denied ones.

### 5.2 Using `fail_fast: true`

For cases where the entire batch must be valid before proceeding, the client MUST:

1. Use `fail_fast: true` to stop processing at the first failure.
2. Evaluate the result: if `processed < total_requests`, there was an early stop.
3. In that case, do not proceed with the actions and resolve the failure before retrying.

### 5.3 `batch_id` idempotency

If the same `batch_id` is submitted twice, the server MUST return the same response as for the first submission (idempotency). This protects against accidental retries in case of network error.

## 6. Error Handling

### 6.1 Batch-level errors (affect the entire batch)

| Code | HTTP | Description |
|---|---|---|
| `BULK-001` | 400 | Batch exceeds maximum size of 100 items |
| `BULK-002` | 429 | Bulk request rate limit exceeded (10/sec per institution) |
| `BULK-004` | 400 | Query result too large; use cursor pagination |

### 6.2 Item-level errors (within a successful batch)

| Code | Description |
|---|---|
| `BULK-003` | One or more requests within the batch failed (see individual results) |

When `BULK-003` occurs, the HTTP response is `207 Multi-Status` and the body contains the individual results, including those that failed. Successfully evaluated results contain their `decision` in the corresponding field.

### 6.3 Batch-level error format

```json
{
  "error": "BULK-001",
  "message": "Batch size exceeds maximum of 100 items. Provided: 143.",
  "batch_id": "bat-uuid-..."
}
```

---

## 7. Query Pagination

### 7.1 Cursor mechanism

Bulk liability query results are paginated using an **opaque cursor**. The cursor:

- Is included in the response when more pages are available.
- Is valid for **10 minutes** from its generation.
- Is sent in the next POST request with the same `query_id` and the same filter parameters.
- If the cursor expires, the query must be restarted from the beginning.

### 7.2 Fetching the next page

```json
{
  "query_id": "qry-uuid-...",
  "agent_ids": ["agt-uuid-aaa", "agt-uuid-bbb", "agt-uuid-ccc"],
  "time_range": {
    "from": "2026-01-01T00:00:00Z",
    "to": "2026-03-10T23:59:59Z"
  },
  "limit": 1000,
  "cursor": "eyJwYWdlIjoyLCJvZmZzZXQiOjEwMDB9"
}
```

The `agent_ids` and `time_range` fields MUST be identical to the original request. The server MAY return HTTP 400 if they differ.

### 7.3 Last page

When the response includes `"cursor": null`, there are no more pages available.

## 8. Ledger Integration

Bulk operations do **NOT generate separate ledger events** for the batch itself. Each approved authorization request within a batch generates an individual `AUTHORIZATION` event in ACP-LEDGER-1.2, in exactly the same way as a unit authorization.

This means:

- A batch of 100 approved authorizations generates 100 `AUTHORIZATION` events in the ledger.
- There is no `BULK_AUTHORIZATION` event in the ledger schema.
- Ledger audits are equivalent for unit and batch authorizations.
- The `batch_id` from the request MAY be included in the ledger event context as optional metadata, to facilitate correlation of events originating from the same batch.
