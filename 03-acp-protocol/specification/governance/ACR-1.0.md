## 1. Purpose

This document specifies the **ACP Compliance Runner** (`acr`), a command-line tool that executes the test suites defined in ACP-TS-1.1 against ACP protocol implementations.

The goals of `acr` are:

- Enable implementers to verify the conformance of their ACP stack in an automated manner.
- Integrate with CI/CD pipelines for continuous validation.
- Produce standardized reports comparable across implementations.
- Serve as an executable reference for ACP-CONF-1.1.

`acr` does not replace manual auditing or formal certification, but constitutes the mandatory first step for any implementation seeking declared conformance.

## 2. CLI Interface

### 2.1 Main command

```bash
acr run --level L3 --target http://localhost:8080 --output json
```

### 2.2 Available flags

| Flag | Description | Default |
|---|---|---|
| `--level` | ACP-CONF-1.1 conformance level to evaluate. Values: `L1`, `L2`, `L3`, `L4`, `L5`, or `all` | `all` |
| `--target` | Base URL of the ACP endpoint under test. MUST include scheme and host | (required) |
| `--output` | Output report format: `json`, `text`, `junit` | `text` |
| `--timeout` | Maximum time per individual test in seconds | `30s` |
| `--skip` | Comma-separated list of `test_id` values to skip (e.g. `TS-L2-003,TS-L3-007`) | (none) |

### 2.3 Usage examples

```bash
# Run only L3 against a local target, JSON output
acr run --level L3 --target http://localhost:8080 --output json

# Run all levels, skip two tests, extended timeout
acr run --level all --target https://acp.mydomain.com --timeout 60s --skip TS-L4-002,TS-L5-001

# JUnit output for CI
acr run --level L5 --target $ACP_TARGET --output junit > acr-results.xml
```

### 2.4 Additional subcommands

| Subcommand | Description |
|---|---|
| `acr list --level L3` | List all available test_ids for the given level |
| `acr version` | Display `acr` version and the ACP-TS version it implements |
| `acr validate-config` | Verify that the target responds at `/acp/v1/health` before running |

## 3. Test Execution

### 3.1 Mechanism

For each test defined in ACP-TS-1.1, `acr`:

1. Constructs the HTTP request from the test's `method`, `path`, `headers`, and `body` fields.
2. Sends the request to the `--target`.
3. Compares the received response against `expected_result` from ACP-TS-1.1 §8, evaluating:
   - HTTP status code
   - Response body structure (required fields present)
   - Specific values where ACP-TS-1.1 mandates them
4. Records `duration_ms` from request send to full response receipt.
5. Determines result: `PASSED`, `FAILED`, or `SKIPPED`.

### 3.2 Timeout handling

If a request exceeds the `--timeout` value, the test is recorded as `FAILED` with `reason: "timeout"` and `acr` proceeds to the next test (the full run is not aborted).

### 3.3 Test dependencies

When a test depends on state generated by a prior test (e.g. registering an agent to then query it), `acr` automatically executes the prerequisite setup if the preceding test was `PASSED`. If setup fails, dependent tests are marked `SKIPPED` with `reason: "prerequisite_failed"`.

### 3.4 Test data

`acr` generates valid synthetic data for each test (UUIDs, names, etc.) unless fixtures are provided via `--fixtures <file.json>`. Synthetic data ensures each run is independent and reproducible.

## 4. Report Format (JSON)

When `--output json`, `acr` writes the following object to stdout:

```json
{
  "acr_version": "1.0.0",
  "ats_version": "1.1",
  "target": "http://localhost:8080",
  "level": "L3",
  "timestamp": "2026-03-10T14:22:00Z",
  "duration_ms": 4320,
  "summary": {
    "total": 47,
    "passed": 44,
    "failed": 2,
    "skipped": 1
  },
  "results": [
    {
      "test_id": "TS-L3-001",
      "name": "Agent registration — minimum data",
      "level": "L3",
      "status": "PASSED",
      "duration_ms": 87,
      "expected_status": 201,
      "actual_status": 201
    },
    {
      "test_id": "TS-L3-012",
      "name": "Capability grant — invalid token",
      "level": "L3",
      "status": "FAILED",
      "duration_ms": 112,
      "expected_status": 401,
      "actual_status": 200,
      "failure_reason": "Endpoint did not reject expired token"
    },
    {
      "test_id": "TS-L3-018",
      "name": "Reputation query — non-existent agent",
      "level": "L3",
      "status": "SKIPPED",
      "reason": "prerequisite_failed"
    }
  ]
}
```

The `results` array follows the ACP-TS-1.1 §8 TestResult format. Additional `acr` fields (`duration_ms`, `failure_reason`) are appended without breaking compatibility.

## 5. JUnit Output

### 5.1 Requirement

When `--output junit`, `acr` MUST produce XML compliant with the standard JUnit schema used by GitHub Actions, Jenkins, and GitLab CI.

### 5.2 XML structure

```xml
<?xml version="1.0" encoding="UTF-8"?>
<testsuites name="ACP Compliance Runner" tests="47" failures="2" skipped="1" time="4.320">
  <testsuite name="ACP-L3" tests="47" failures="2" skipped="1" time="4.320">
    <testcase classname="acp.l3" name="TS-L3-001: Agent registration — minimum data" time="0.087">
    </testcase>
    <testcase classname="acp.l3" name="TS-L3-012: Capability grant — invalid token" time="0.112">
      <failure message="HTTP 200, expected 401">
        Endpoint did not reject expired token. Response: {"status":"ok"}
      </failure>
    </testcase>
    <testcase classname="acp.l3" name="TS-L3-018: Reputation query — non-existent agent" time="0">
      <skipped message="prerequisite_failed"/>
    </testcase>
  </testsuite>
</testsuites>
```

### 5.3 Guaranteed compatibility

`acr` guarantees compatibility with:

- GitHub Actions (`junit-report` action)
- Jenkins (JUnit Publisher plugin)
- GitLab CI (`junit` artifact reports)
- CircleCI (JUnit test results)

## 6. Exit Codes

| Code | Meaning |
|---|---|
| `0` | All executed tests passed (no `FAILED` results) |
| `1` | One or more tests failed |
| `2` | Tool error: target unreachable, invalid configuration, global timeout |

Exit codes enable direct integration with CI systems without requiring report parsing.

```bash
acr run --level L5 --target $ACP_TARGET --output junit
if [ $? -eq 1 ]; then
  echo "Conformance failures detected"
  exit 1
fi
```

## 7. CI Integration

### 7.1 GitHub Actions — example workflow

```yaml
name: ACP Compliance Check

on:
  push:
    branches: [main, develop]
  pull_request:

jobs:
  acp-compliance:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Install ACP Compliance Runner
        run: |
          curl -sSL https://github.com/acp-protocol/acr/releases/latest/download/install.sh | bash

      - name: Start ACP server (target)
        run: |
          docker compose up -d acp-server
          sleep 5

      - name: Run L5 conformance suite
        run: |
          acr run --level L5 --target ${{ env.ACP_TARGET }} --output junit > acr-results.xml
        env:
          ACP_TARGET: http://localhost:8080

      - name: Publish results
        uses: mikepenz/action-junit-report@v4
        if: always()
        with:
          report_paths: acr-results.xml
          check_name: ACP Conformance L5
          fail_on_failure: true
```

### 7.2 GitLab CI

```yaml
acp-compliance:
  image: node:20-alpine
  script:
    - npm install -g @acp-protocol/acr
    - acr run --level L5 --target $ACP_TARGET --output junit > acr-results.xml
  artifacts:
    reports:
      junit: acr-results.xml
```

### 8.2 Tool requirements

An `acr` implementation claiming conformance with this document MUST:

- Implement all flags defined in §2.2.
- Execute all ACP-TS-1.1 tests for the specified level.
- Produce JSON output exactly matching the schema in §4.
- Produce valid JUnit output per §5.
- Return the exit codes defined in §6.

### 8.3 Versioning

`acr` versions independently from the ACP protocol. Each `acr` release declares which ACP-TS version it implements via the `ats_version` field in the output report.
