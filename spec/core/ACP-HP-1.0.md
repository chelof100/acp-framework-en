# ACP-HP-1.0
## Handshake Protocol Specification
**Status:** Draft
**Version:** 1.0
**Depends-on:** ACP-SIGN-1.0, ACP-CT-1.0, ACP-ITA-1.0
**Required-by:** ACP-API-1.0, ACP-CONF-1.0

---

## 1. Scope

This document defines the procedure by which an ACP agent proves to a receiving system that it possesses the private key corresponding to the `sub` of a presented Capability Token.

ACP-HP-1.0 is stateless. It does not establish sessions. It produces no session_id. It requires no server-side state between requests.

The handshake occurs in the context of each request that presents a CT. Its sole purpose is to cryptographically bind the CT bearer to their declared identity.

Without ACP-HP-1.0, a stolen CT is sufficient to impersonate an agent. With ACP-HP-1.0, the bearer must demonstrate possession of `sk_sub` on every request.

---

## 2. Definitions

**Initiator (I):** Agent that presents the CT and proves key possession.

**Responder (R):** System that verifies the proof and decides whether to proceed.

**Challenge:** Random value generated by R, single-use, with a short validity window.

**Proof-of-Possession (PoP):** The Initiator's signature over the challenge and the request, demonstrating possession of `sk_sub`.

**Binding:** Cryptographic linkage between the CT, challenge, and request content.

---

## 3. Security Model

ACP-HP-1.0 guarantees the following properties when executed correctly:

```
P1 — Identity authentication
     The CT bearer possesses sk_sub corresponding to the token's sub.

P2 — Request binding
     The proof is bound to the content of the specific request.
     A valid PoP for request A is not valid for request B.

P3 — Anti-replay protection
     A used challenge cannot be reused.

P4 — Channel independence
     The protocol does not rely on transport channel properties
     for identity guarantees.
```

---

## 4. Prerequisites

**The Initiator MUST:**
- Possess an Ed25519 key pair `(sk_sub, pk_sub)`
- Have a valid CT where `sub == base58(SHA-256(pk_sub))`
- Have access to the Responder's challenge endpoint

**The Responder MUST:**
- Expose the endpoints defined in §6
- Maintain a registry of issued unused challenges (active window)
- Have access to the ITA to resolve `pk_sub` per ACP-ITA-1.0

**Transport channel:**
- MUST be HTTPS
- mTLS SHOULD be used in B2B environments

---

## 5. Protocol Sequence

```
Initiator (I)                              Responder (R)
     │                                          │
     │   POST /acp/v1/handshake/challenge       │
     │ ────────────────────────────────────►    │
     │                                          │  generates challenge
     │                                          │  registers in active window
     │   {challenge_id, challenge, expires_at}  │
     │ ◄────────────────────────────────────    │
     │                                          │
     │  builds PoP payload                      │
     │  signs with sk_sub                       │
     │                                          │
     │   POST /acp/v1/<endpoint>                │
     │   Authorization: ACP-Agent <CT>          │
     │   X-ACP-PoP: <pop_token>                 │
     │ ────────────────────────────────────►    │
     │                                          │  verifies pop_token
     │                                          │  verifies CT
     │                                          │  removes challenge from window
     │   {response}                             │
     │ ◄────────────────────────────────────    │
```

---

## 6. Responder Endpoints

### `POST /acp/v1/handshake/challenge`

Issues a challenge for use in the next request.

**No authentication required.**

**Request body:**
```json
{
  "agent_id": "<AgentID_of_initiator>",
  "resource": "org.example/accounts/ACC-001",
  "capability": "acp:cap:financial.payment"
}
```

`resource` and `capability` are informational. They allow the Responder to issue pre-contextualized challenges. They are not binding — the actual binding occurs in the PoP Token.

**Response 200:**
```json
{
  "challenge_id": "<uuid_v4>",
  "challenge": "<128_bits_CSPRNG_base64url>",
  "expires_at": 1718920030,
  "responder_id": "<institution_id_of_responder>"
}
```

`expires_at` MUST be `issued_at + 30 seconds`. This value is fixed in v1.0.

**Errors:**

| HTTP | Code | Condition |
|------|--------|-----------|
| 400 | HP-001 | Malformed agent_id |
| 429 | HP-002 | Challenge rate limit for this agent_id |
| 503 | HP-003 | Challenge registry unavailable |

---

## 7. PoP Token Structure

The PoP Token is the artifact that proves possession of `sk_sub`. It is transmitted in the `X-ACP-PoP` header.

```json
{
  "ver": "1.0",
  "challenge_id": "<uuid_of_challenge>",
  "challenge": "<challenge_value>",
  "agent_id": "<AgentID_of_initiator>",
  "request_method": "POST",
  "request_path": "/acp/v1/authorize",
  "request_body_hash": "<SHA-256_base64url_of_body>",
  "issued_at": 1718920010,
  "sig": "<base64url_Ed25519_signature_of_sk_sub>"
}
```

**Transmission:**

The PoP Token serialized as JSON MUST be encoded in base64url and transmitted in the header:

```http
X-ACP-PoP: <base64url(JSON(pop_token))>
```

---

## 8. PoP Token Field Specification

**8.1 `ver`** — MUST be `"1.0"`.

**8.2 `challenge_id`** — UUID of the challenge issued by the Responder. MUST correspond to an active challenge in the Responder's window.

**8.3 `challenge`** — Challenge value. The Responder MUST verify that it matches the one registered for `challenge_id`.

**8.4 `agent_id`** — MUST match the `sub` of the CT presented in `Authorization`.

**8.5 `request_method`** — HTTP method of the request. MUST match the actual method received.

**8.6 `request_path`** — Request path without query string. MUST match the actual path received.

**8.7 `request_body_hash`** — `base64url(SHA-256(body_bytes))`. For requests without a body: `base64url(SHA-256(""))`.

This field is the binding between the PoP and the specific request content. It prevents a valid PoP from being reused with a different body.

**8.8 `issued_at`** — Unix timestamp in seconds. MUST be ≤ `challenge.expires_at`. MUST be ≥ `challenge.issued_at`.

**8.9 `sig`** — The Initiator's signature with `sk_sub` over all fields except `sig`, per ACP-SIGN-1.0.

---

## 9. PoP Token Construction Procedure (Initiator)

```
1. Obtain challenge via POST /acp/v1/handshake/challenge
2. Build PoP object with all fields except sig
3. issued_at = current timestamp
4. request_body_hash = base64url(SHA-256(exact_body_bytes))
5. Sign per ACP-SIGN-1.0 with sk_sub
6. Serialize to JSON
7. Encode in base64url
8. Include in header X-ACP-PoP
9. Include CT in header Authorization: ACP-Agent <CT>
10. Send request
```

---

## 10. Verification Procedure (Responder)

The following steps MUST be executed in exact order. A failure at any step MUST produce rejection with the corresponding code.

```
Step 1:  Extract CT from Authorization header
Step 2:  Extract and decode PoP Token from X-ACP-PoP header
Step 3:  Verify pop.ver == "1.0"
Step 4:  Verify pop.challenge_id exists in the active window
Step 5:  Verify pop.challenge == challenge registered for challenge_id
Step 6:  Resolve pk_sub from pop.agent_id via ACP-ITA-1.0 or agent registry
Step 7:  Verify pop.sig signature with pk_sub per ACP-SIGN-1.0
Step 8:  Verify pop.agent_id == CT.sub
Step 9:  Verify pop.issued_at <= challenge.expires_at
Step 10: Verify pop.request_method == received HTTP method
Step 11: Verify pop.request_path == received HTTP path
Step 12: Compute received_hash = base64url(SHA-256(received_body))
         Verify received_hash == pop.request_body_hash
Step 13: Remove challenge_id from active window (consumed, not reusable)
Step 14: Continue with CT validation per ACP-CT-1.0 §6
```

Steps 1–13 MUST be completed before step 14. CT verification depends on the bearer's identity already having been proven.

---

## 11. Challenge Registry

The Responder MUST maintain an in-memory registry of active challenges.

**Per-entry structure:**

```json
{
  "challenge_id": "<uuid>",
  "challenge": "<base64url_value>",
  "agent_id": "<AgentID>",
  "issued_at": 1718920000,
  "expires_at": 1718920030
}
```

**Management rules:**

The Responder MUST remove an entry when:
- It is consumed (step 13 of the verification procedure)
- `expires_at` is reached without being consumed

The Responder MUST reject presentation of a `challenge_id` that does not exist in the active registry, regardless of whether it was consumed or expired. The error code differs for each case (§12).

**Limit of active challenges per agent_id:** The Responder MAY limit the number of simultaneously active challenges per agent_id. Recommended value: 5. When the limit is reached, POST /challenge MUST return HP-002.

---

## 12. Errors

| Code | HTTP | Condition |
|--------|------|-----------|
| HP-001 | 400 | Malformed agent_id in challenge request |
| HP-002 | 429 | Active challenge limit for agent_id |
| HP-003 | 503 | Challenge registry unavailable |
| HP-004 | 400 | X-ACP-PoP header absent |
| HP-005 | 400 | Malformed or undecodable PoP Token |
| HP-006 | 400 | Unsupported ver |
| HP-007 | 401 | challenge_id not found — expired or already consumed |
| HP-008 | 401 | challenge value does not match |
| HP-009 | 401 | Invalid PoP signature |
| HP-010 | 401 | agent_id in PoP does not match CT sub |
| HP-011 | 401 | PoP issued_at outside challenge window |
| HP-012 | 400 | request_method does not match |
| HP-013 | 400 | request_path does not match |
| HP-014 | 400 | request_body_hash does not match |
| HP-015 | 401 | pk_sub not resolvable for agent_id |

HP-007 is intentionally ambiguous between expired and consumed. The Initiator is not told which of the two occurred.

---

## 13. Anti-Replay Protection

The combination of the following mechanisms guarantees P3:

**Single-use challenge:** Step 13 of the verification procedure removes the challenge upon consumption. A second request with the same challenge_id will produce HP-007.

**30-second window:** An expired challenge produces HP-007. The Initiator must obtain a new challenge for each request.

**Body hash binding:** `request_body_hash` binds the PoP to the exact request content. Modifying the body invalidates the PoP.

**Method and path binding:** `request_method` and `request_path` bind the PoP to the specific endpoint. A valid PoP for POST /authorize is not valid for POST /tokens.

---

## 14. Behavior Under Anomalous Conditions

| Condition | MUST behavior |
|-----------|-------------------|
| X-ACP-PoP header absent | Reject HP-004 |
| Expired challenge | Reject HP-007 — do not reveal whether expired or consumed |
| Already consumed challenge | Reject HP-007 — do not reveal whether expired or consumed |
| pk_sub not resolvable | Reject HP-015 — do not continue with CT |
| Received body differs from hashed body | Reject HP-014 |
| Challenge registry unavailable | Reject HP-003 — fail closed |
| PoP with issued_at in the future | Reject HP-011 |

The Responder MUST fail closed. If the challenge registry is unavailable, there is no way to verify the PoP, so all requests must be rejected.

---

## 15. Relationship with ACP-API-1.0

ACP-HP-1.0 operates as a pre-verification layer before ACP-API-1.0. The combined flow is:

```
Request arrives at ACP server
  │
  ├─ Step 1: ACP-HP-1.0 verifies PoP (steps 1–13)
  │          If fails → reject HP-0xx
  │
  ├─ Step 2: ACP-CT-1.0 verifies CT (§6)
  │          If fails → reject CT-0xx / AUTH-0xx
  │
  ├─ Step 3: ACP-RISK-1.0 evaluates risk
  │
  └─ Step 4: Process request
```

ACP-API-1.0 endpoints that require authentication MUST also require a valid `X-ACP-PoP`. The exceptions are `GET /acp/v1/health` and `POST /acp/v1/handshake/challenge`.

## 16. Implementation Considerations

**Challenge rate limiting:** The POST /challenge endpoint MUST have rate limiting independent of ACP-API-1.0 rate limiting. Recommended: 20 challenges/minute per agent_id.

**Clock synchronization:** The `issued_at` field of the PoP has no explicit drift tolerance. The Responder SHOULD apply the same 300-second tolerance defined in ACP-CT-1.0 §5.6 for `iat`. If the Initiator's clock has excessive drift, the challenge may expire before the PoP arrives.

**Stateless Responder implementation:** The challenge registry is the only state that ACP-HP-1.0 requires on the server. If the Responder needs to be horizontally scalable, the challenge registry MUST be shared across instances (e.g., Redis with a 30-second TTL). Without a shared registry, a challenge issued by instance A cannot be verified by instance B.

---

## 17. Conformance

An implementation is ACP-HP-1.0 conformant if it:

- Exposes `POST /acp/v1/handshake/challenge` with the structure of §6
- Issues 128-bit CSPRNG challenges with a 30-second window
- Verifies the PoP Token in the exact order of §10
- Removes the challenge upon consumption (step 13)
- Rejects expired or already consumed challenges with HP-007
- Fails closed when the challenge registry is unavailable
- Produces the error codes of §12
- Requires X-ACP-PoP on all authenticated endpoints except those declared in §15
