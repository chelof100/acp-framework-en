# ACP-CT-1.0
## Capability Token Specification
**Status:** Draft
**Version:** 1.0
**Depends-on:** ACP-SIGN-1.0, ACP-CAP-REG-1.0
**Required-by:** ACP-RISK-1.0, ACP-REV-1.0, ACP-API-1.0

---

## 1. Scope

This document defines the structure, fields, verification procedure, and delegation rules of ACP Capability Tokens. A Capability Token is the primary artifact that authorizes an agent to perform actions on specific resources.

---

## 2. Definitions

**AgentID:** Unique identifier of an agent. MUST be `base58(SHA-256(pk_bytes))` where `pk_bytes` are the 32 bytes of the agent's Ed25519 public key.

**Issuer:** Agent that issues the token and signs it with their private key.

**Subject:** Agent to whom the token capabilities are granted.

**Capability:** Identifier of an authorized action. Format per ACP-CAP-REG-1.0.

**Delegation chain:** Sequence of tokens where each token is issued by the subject of the previous token.

---

## 3. AgentID Format

```
AgentID = base58(SHA-256(pk_bytes))
```

where:
- `pk_bytes` = Ed25519 public key, 32 bytes in raw format
- `SHA-256` produces 32 bytes
- `base58` uses the Bitcoin alphabet: `123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz`

Typical output: 43-44 characters.

---

## 4. Token Structure

```json
{
  "ver": "1.0",
  "iss": "<AgentID_issuer>",
  "sub": "<AgentID_subject>",
  "cap": ["acp:cap:financial.payment"],
  "res": "org.example/accounts/ACC-001",
  "iat": 1718920000,
  "exp": 1718923600,
  "nonce": "<128bit_CSPRNG_base64url>",
  "deleg": {
    "allowed": false,
    "max_depth": 0
  },
  "parent_hash": null,
  "constraints": {},
  "rev": {
    "type": "endpoint",
    "uri": "https://acp.example.com/acp/v1/rev/check"
  },
  "sig": "<base64url_Ed25519_signature>"
}
```

## 5. Field Specification

**5.1 `ver`** — MUST be `"1.0"`.

**5.2 `iss`** — AgentID of the issuer. MUST be a valid AgentID per §3. The issuer signs the token with their `sk_iss`.

**5.3 `sub`** — AgentID of the subject. MUST be a valid AgentID. The subject MUST demonstrate possession of `sk_sub` during the handshake per ACP-HP-1.0.

**5.4 `cap`** — Non-empty array of capability identifiers. Each element MUST be valid per ACP-CAP-REG-1.0. MUST NOT be empty.

**5.5 `res`** — Identifier of the resource to which the capabilities apply. Format: `<institution_domain>/<resource_path>`. MUST be a non-empty string.

**5.6 `iat`** — Unix timestamp in seconds. Time of issuance. MUST be ≤ current timestamp at verification (maximum tolerance: 300 seconds for clock drift).

**5.7 `exp`** — Unix timestamp in seconds. Expiration time. MUST be > `iat`. MUST be > current timestamp at verification.

**5.8 `nonce`** — 128 bits generated by CSPRNG, encoded in base64url without padding. MUST be unique. Used for replay prevention.

**5.9 `deleg`** — Object with two fields:
- `allowed`: boolean. If `false`, the subject cannot delegate this token.
- `max_depth`: integer ≥ 0. Maximum remaining delegation depth. MUST be 0 if `allowed` is `false`.

**5.10 `parent_hash`** — Null for root tokens. For delegated tokens, MUST be `base64url(SHA-256(JCS(parent_token_without_sig)))`.

**5.11 `constraints`** — Object with additional restrictions per capability. May be empty `{}`. Mandatory constraints per capability are defined in ACP-CAP-REG-1.0 §5.

**5.12 `rev`** — Object with revocation information:
- `type`: MUST be `"endpoint"` or `"crl"`
- `uri`: URL of the verification endpoint or CRL per ACP-REV-1.0

**5.13 `sig`** — Issuer's signature per ACP-SIGN-1.0. Covers all fields except `sig`.

---

## 6. Verification Procedure

The following steps MUST be executed in exact order:

```
Step 1: Verify ver == "1.0"
Step 2: Verify sig signature with pk_iss per ACP-SIGN-1.0
Step 3: Verify current timestamp <= exp
Step 4: Verify current timestamp >= iat - 300
Step 5: Verify revocation status per ACP-REV-1.0
Step 6: Verify that requested capability ∈ cap
Step 7: Verify that requested resource is covered by res
Step 8: If token is delegated, verify parent_hash
Step 9: Verify constraints per ACP-CAP-REG-1.0
```

A failure at any step MUST produce immediate rejection without continuing.

---

## 7. Delegation Rules

When subject S1 of token T1 issues a delegated token T2 for subject S2:

```
Mandatory constraints:
  cap(T2) ⊆ cap(T1)              — subset of capabilities
  res(T2) ⊆ res(T1)              — subset of resources
  exp(T2) ≤ exp(T1)              — cannot extend expiration
  max_depth(T2) < max_depth(T1)  — depth is reduced by 1
  parent_hash(T2) = SHA-256(JCS(T1 without sig))
```

If any constraint is violated, T2 MUST be rejected.

**Absolute depth limit:** max_depth MUST NOT exceed 8 in any token. This limit is fixed and non-configurable.

---

## 8. Errors

| Code | Condition |
|--------|-----------|
| CT-001 | Unsupported ver |
| CT-002 | Invalid signature |
| CT-003 | Token expired |
| CT-004 | Token not yet valid (iat in the future) |
| CT-005 | Capability not present in token |
| CT-006 | Resource not covered by token |
| CT-007 | Delegation not permitted (deleg.allowed == false) |
| CT-008 | max_depth exceeded |
| CT-009 | Invalid parent_hash |
| CT-010 | Token revoked |
| CT-011 | Constraint violated |
| CT-012 | Empty cap array |
| CT-013 | Malformed AgentID |

---

## 9. Conformance

An implementation is ACP-CT-1.0 conformant if it:

- Generates AgentIDs per §3
- Produces tokens with all MUST fields
- Executes verification in the exact order of §6
- Applies delegation rules of §7
- Verifies the complete delegation chain back to the root token
- Rejects tokens with max_depth > 8
- Produces the error codes of §8
